# 楼宇交通 · 电梯派梯策略对比仿真

在**同一批客流**下对照三种电梯派梯策略，用 SimPy 做离散事件仿真，FastAPI 提供服务，
PostgreSQL 保存楼层需求、轿厢容量、开关门耗时与随机种子，React 重放事件日志呈现
井道、候梯队列和乘客轨迹。**不连接任何真实电梯，也不播放随机楼层动画** —— 前端
画面是后端确定性事件日志的逐帧重放。

## 教学目标与对应实现

| 要求 | 实现 |
|---|---|
| 比较派梯策略，而非随机楼层动画 | 三种策略共用同一物理引擎；前端只重放 `events` 日志，帧状态全部由事件推导（`replay.js`） |
| React 呈现井道、候梯队列、乘客轨迹 | `Shaft.jsx`（井道/轿厢/队列/指派灯）、`PassengerAudit.jsx`（每名乘客位置迁移链） |
| FastAPI 调用 SimPy | `backend/app/main.py` → `runner.py` → `engine.py`（SimPy 进程） |
| PostgreSQL 保存楼层需求、容量、门时、随机种子 | 表 `scenarios / runs / passengers / events`（`database.py`） |
| 乘客有起终层与到达时间 | `models.Pax(origin, dest, arrival_time)`；泊松到达生成器 `demand.py` |
| 轿厢方向和停站顺序决定是否可接 | `policies.py` 的 SCAN 决策：载客车只接同方向队列，空车可换向接客；`engine._eligible` |
| 满载后未上车者留在原队列 | HallCall FIFO 保留剩余乘客，产生 `car_full` 事件，位置仍是 `hall:楼层` |
| 指标区分候梯/乘梯/总行程 | 指标表三列分开：候梯=到达→登乘，乘梯=登乘→离开，总行程=两者之和 |
| 仿真结束未服务乘客不能被剔除 | `all_pax.*` 全客流口径按截止时刻计入 UNSERVED；`served_only.*` 显式标注条件均值 |
| 早高峰上行 / 跨层需求 / 长开门案例 | `demand.SCENARIO_DEFAULTS` 三个案例；长开门与跨层同种子同客流、只改门时 |
| 同一客流对照策略 | API 只生成一次到达序列，`arrivals_override` 传给每个策略 |
| 事件日志核对每名乘客只在一个物理位置 | `verifier.py` 逐事件重建位置并校验，前端 `auditFrame` 二次核对 |

## 三种策略

1. **集选 SCAN（collective）**：无全局指派，每台梯沿单一方向扫描内呼与同向外呼，
   到端层再反向；各梯可重复响应同一呼梯（对照组，体现无协调的重复停站）。
2. **最近梯 ETA（nearest）**：新外呼按预估到达时间全局指派给最近轿厢；长队列
   （剩余人数 > 容量一半）空闲梯会主动补位，避免大堂"一梯往返、其余观望"；
   认领车满载驶离时释放呼叫重派。
3. **高低区分区（zoning）**：楼层均分给各轿厢固定区段，本区呼叫只派本区车，
   本区车满载时才允许越区支援。

三者物理参数（速度、容量、开关门时间）完全相同，差别只在决策钩子。

## 使用方式

1. 选择案例（早高峰上行 / 跨层需求 / 长开门时间），可调楼层、轿厢数、容量、
   层间耗时、开关门耗时、到达率、随机种子、仿真截止时间；
2. 勾选要对比的策略，点击"同一客流运行对比"——三个策略跑的是**同一份到达序列**；
3. 查看指标对比表（绿色为该列最优，红色表示有未服务乘客）；
4. 在策略标签间切换，用时间轴播放井道：轿厢逐层移动、开关门、内呼灯、
   候梯队列、呼叫指派（→n#）与补位（+n#）；
5. 在"乘客轨迹核对"面板点任一乘客，右侧显示其唯一位置链：
   `候梯厅 o层 → k号轿厢内 → 系统外 d层（到达）`；状态胶囊可筛选未服务乘客。

## 指标口径（重要）

- **全客流口径 `all_pax`**：对所有乘客统计。仿真结束时仍在候梯或梯内的乘客
  标记 `UNSERVED`，等待/总行程时间按截止时刻截断计入，**不得删除**。所以未服务
  越多，该口径数值越差，无法靠丢弃乘客美化策略。
- **已完成口径 `served_only`**：只对到达目的层的乘客求条件均值（乘梯时间只有
  完成者有完整物理意义），表格中明确用 `**` 标注，不与全客流口径混用。
- 对每名完成乘客恒有：`总行程 = 候梯 + 乘梯`（测试断言）。

## 参考结果（12 层 / 4 梯 / 容量 8 / 层间 2s）

| 案例 | 策略 | 服务/需求 | 未服务 | 候梯均值 | 乘梯均值 | 总行程均值 |
|---|---|---|---|---|---|---|
| 早高峰 22人/分·门4s | collective | 308/308 | 0 | 41.5s | 25.5s | 67.0s |
| 早高峰 | **nearest** | 308/308 | 0 | **28.1s** | 24.2s | **52.3s** |
| 早高峰 | zoning | 132/308 | **176** | 605.9s | 22.3s | 615.4s |
| 跨层 16人/分·门4s | **collective** | 303/303 | 0 | **16.4s** | 19.2s | **35.6s** |
| 跨层 | nearest | 303/303 | 0 | 33.5s | 16.8s | 50.3s |
| 跨层·门12s | collective | 303/303 | 0 | 97.5s | 93.0s | 190.6s |
| 跨层·门12s | **nearest** | 303/303 | 0 | 101.0s | 50.6s | **151.6s** |
| 跨层·门12s | zoning | 295/303 | 8 | 164.8s | 45.5s | 209.2s |

教学结论：早高峰单向密集上行时全局指派（nearest）最优，静态分区因大堂全归低区
一辆车而严重积压；均衡混流下集选简单且有效；长开门放大停站代价，nearest 因减少
重复停站使总行程反超，但静态分区在压力下最先出现未服务乘客。

## 门保持打开（乘客挡门）事件

评估高峰期一台轿厢的门被乘客短暂挡住对整体候梯的影响。在前端配置或通过
`POST /api/simulate` 的 `blocks` 字段指定**若干个**事件：

```json
"blocks": [{"car": 0, "floor": 4, "start": 200, "end": 280}]
```

- 语义：`start` 时刻**武装**指定轿厢（记录 `door_block_arm`）：关门逐层就位到
  指定楼层（门已在该层正常停站则不重开、不重复登乘，直接续接保持），执行一次
  与普通停站相同的开门—先下后上（一批 FIFO 登乘），随后记录
  **`door_block_start`**；到 `end` 记录 **`door_block_end`** 并关门。
- **保持期间**（start→end）该轿厢不能移动、不能重复登乘（新到乘客留在候梯队列）、
  车内乘客位置不变；**其他轿厢完全不受影响**，继续按各自策略运行，
  nearest/zoning 会把被挡轿厢持有的呼叫释放并派给其他轿厢。
- 若 start 落在一层移动中途，当前这层移动走完再就位，**不回退、不跳层**；
  配置楼层与实际楼层不符时在实际层执行并产生校验告警（在无阻挡重放时间轴上
  取点配置可保证吻合：start 之前仿真与无阻挡完全一致）。
- `compare_baseline=true`（默认）时每个策略额外跑一次**无阻挡对照**，
  与阻挡运行、三种策略共用**同一份到达序列**（同种子，只生成一次乘客），
  返回 `baselines / baseline_comparison / deltas`，指标同时给出
  **受影响乘客子口径**（保持期间滞留阻挡楼层的人 + 门开时车内被延后的人）
  与**全客流口径**，两者并列、互不替换。
- 前端时间轴以红色斜纹段显示阻挡区间（点击跳转到阻挡开始帧），被挡轿厢红色
  脉冲描边、方向符变 ✋；可在"阻挡运行 / 无阻挡对照"间切换重放。
- 阻挡配置随 run 持久化（`runs.blocks_json / blocked / baseline_run_id`、
  `scenarios.blocks_json`），刷新后从事件日志确定性重放出相同的阻挡状态与指标。

相关实现：`blockages.py`（配置校验）、`engine.py`（武装/就位/保持/解除过程）、
`verifier.py`（保持期间禁动/禁关门/禁重复登乘、位置不跳变硬校验）。

## 事件日志与物理不变量

每次仿真输出带时间戳的事件流：`pax_arrive / call_assign / car_dir / car_move /
doors_open / pax_board / car_full / pax_alight / doors_close / pax_unserved`，
阻挡运行额外有 `door_block_arm / door_block_start / door_block_end`
（就位移动带 `blocked_relocating`，超时未执行有 `door_block_skip_expired`）。

`verifier.py` 逐事件重建世界并硬校验：

1. 任意时刻每名乘客恰好一个物理位置（候梯厅某层 / 某轿厢 / 系统外）；
2. 上车前必须在同层候梯，下车前必须在该梯内，轿厢必须停靠同层；
3. 任何上车事件后车内人数 ≤ 容量；
4. 轿厢每次只移动一层、不越出井道、开门时不移动；
5. 状态链 `arrive → board → alight` 每人至多一次，无重复服务/凭空消失；
6. 日志完成人数与乘客表、指标一致（伪造日志会被测试抓住）；
7. 阻挡保持期间轿厢不移动、不关门、登乘只发生在保持开始前的一批，
   武装后只允许朝目标层逐层就位，每个配置阻挡必须有开始与解除、
   解除时刻严格等于配置 `end`、保持期间楼层不变。

## 目录结构

```
backend/app/
  engine.py     SimPy 物理引擎（移动/开关门/先下后上/FIFO/容量/指标/阻挡过程）
  blockages.py  门保持打开事件配置与校验（指定轿厢/楼层/时间窗）
  policies.py   collective / nearest / zoning 三个策略（阻挡车不参与新指派）
  demand.py     早高峰、跨层、长开门客流（泊松到达，种子可复现）
  models.py     Pax / HallCall / 状态枚举
  verifier.py   事件日志物理不变量校验（含阻挡禁动/禁重复登乘）
  database.py   PostgreSQL 表与持久化（含阻挡配置与对照 run 关联）
  runner.py     组装一次仿真
  main.py       FastAPI：/api/simulate（有/无阻挡同客流）、/api/runs、events
frontend/src/
  engine/replay.js  事件日志 → 逐帧世界快照（确定性，无随机，含阻挡状态）
  components/       Shaft / MetricsTable / PassengerAudit
  App.jsx           阻挡配置、阻挡时间轴、有/无阻挡对照切换
scripts/        setup.sh、start.sh
```
